# FocusFlow — финансовый калькулятор v2.0
Статус: целевая спецификация реализации MVP. Валюта MVP — RUB. Хранение MVP — localStorage; облако и банковские интеграции вне scope.

## 1. Продуктовая задача
Раздел отвечает на вопрос: «Сколько денег у меня есть, какие обязательства предстоят и сколько я могу безопасно тратить до следующего дохода?». Это планировщик денежного потока, не банк и не бухгалтерия.

## 2. Навигация
1. **Сейчас** — расчётный остаток, дневной ориентир, прогноз до следующего дохода, ближайшие обязательства, цели и долги.
2. **Движение** — фактические доходы/расходы, смысловые категории, история операций, поиск и фильтры.
3. **Планы** — регулярные и разовые события, цели накопления, долги к выплате и получению.

Не создаём счета, кошельки, переводы, банковскую сверку, бюджетные лимиты по десяткам категорий или отдельную вкладку аналитики.

## 3. Термины и модель
Все денежные значения — целые копейки (integer). В UI показываем рубли.
- settings.moneyNow — сумма, вручную сверенная пользователем на дату moneyNowDate.
- moneyNowMode=manual: операции не меняют сверенную сумму; пользователь периодически обновляет её.
- moneyNowMode=auto: расчётный остаток = moneyNow + доходы − расходы по операциям с датой строго позже moneyNowDate. Переключение режима не меняет базовую сумму/дату.
- events: regular, one_time, goal, debt_i_owe, debt_owed_to_me. Для регулярного события хранится правило и ближайшая дата; конкретные исполнения отражаются операциями.
- operations: неизменяемые по смыслу факты доходов/расходов, положительная сумма, направление задаёт знак. eventId связывает факт с планом. Категории: mandatory, desired, emergency.
- прогресс цели/долга изменяется только связанной операцией; ручной стартовый прогресс допускается при создании как начальное состояние.

## 4. Прогноз
1. Найти ближайший ожидаемый доход: ближайшее наступление активного события regular/one_time с direction=income. Ручная дата/сумма — резервный источник, если события дохода нет.
2. Рассчитать текущий остаток по выбранному режиму.
3. Сложить обязательные события-расходы, наступающие от сегодня до даты дохода включительно. Для повторяющихся событий перечислить каждое наступление; one_time учитывается один раз.
4. available = currentBalance + nextIncomeAmount − mandatoryEvents.
5. daysLeft = max(1, календарная разница между сегодня и датой дохода). dailyLimit = max(0, floor(available / daysLeft)). Это равномерный ориентир на период, не разрешение тратить всю сумму сегодня.
6. Средний переменный расход считается по календарному окну avgDailyWindowDays, включая дни без операций как нулевые; обязательные расходы из фактических операций исключаются, потому что будущие обязательные события уже зарезервированы отдельно. forecastLeft = available − averageDailySpend × daysLeft.
7. Для статуса нужно минимум 3 разных календарных дня с операциями за окно. Иначе gray.
8. green: forecastLeft >= 0 и доля остатка от ближайшего дохода >15%; yellow: forecastLeft >=0 и доля <=15%; orange: прогноз отрицательный, а желаемые расходы за окно не меньше дефицита; red: прогноз отрицательный и желаемых расходов недостаточно для покрытия дефицита. Если нет дохода — gray.
9. Цвет всегда сопровождается числами, объяснением причины и следующим действием. Это сценарная оценка, не финансовая рекомендация.

## 5. События и регулярность
- regular: direction, amount, category, mandatory flag, recurrence weekly/monthly/yearly, nextDate.
- one_time: разовое поступление или расход с датой.
- goal: целевая сумма, текущий прогресс, необязательный дедлайн.
- debt_i_owe / debt_owed_to_me: общая сумма и уже погашенная/полученная часть.
- Регулярное правило не является фактом списания. Факт появляется только после явного действия пользователя «Отметить выполненным/полученным».
- После исполнения создаётся одна операция с eventId и occurrenceDate; повторное действие для того же eventId+occurrenceDate идемпотентно; nextDate сдвигается на один период.
- Пропуск/перенос наступления не создаёт операцию. Пользователь может изменить дату следующего наступления.
- Цели/долги не резервируют деньги автоматически и не входят в обязательные события прогноза без отдельного планового события.

## 6. Операции
Форма: сумма и направление, категория, название, дата, комментарий. Категории:
- mandatory — необходимое;
- desired — желаемое;
- emergency — непредвиденное.
История сгруппирована по дате, поиск по названию/комментарию, фильтры по периоду/направлению/категории, первая порция 20 с дальнейшей подгрузкой. Редактирование обновляет запись. Удаление связанной операции откатывает прогресс события. В MVP нет счетов и переводов.

## 7. Цели и долги
Пользователь задаёт произвольное название, тип, сумму и необязательный срок. Частичное пополнение/погашение/получение создаёт связанную операцию. Для savings пополнение трактуется как расход/перераспределение в рамках личного денежного потока только если деньги реально покинули доступный остаток; MVP предлагает выбрать категорию и не считает внутреннее резервирование новым активом. Нельзя прибавлять цель к текущему остатку повторно.

## 8. Интеграция с FocusFlow
Платёжное событие может создать связанную задачу; задача содержит linkedEventId и occurrenceDate. Отметка задачи создаёт операцию идемпотентно. Изменение/удаление события синхронизируется с задачей без удаления финансовой истории. Реализация интеграции — после стабилизации ядра; в текущем релизе ручное исполнение события.

## 9. Даты и локальное время
Даты событий и операций — календарные даты YYYY-MM-DD, не UTC timestamp. Это исключает сдвиг даты из-за часового пояса для финансовых дней. Время создания/изменения — ISO timestamp. Сегодня вычисляется в локальном часовом поясе пользователя. Поле timezone хранит IANA ID для будущей синхронизации.

## 10. Миграция
Старые v2 accounts/transactions/goals/liabilities/recurring мигрируются без потери истории. Текущий суммарный баланс счетов становится базовым moneyNow на дату миграции; старые операции сохраняются в истории, но не суммируются повторно относительно новой базовой точки. Счета/переводы/бюджеты больше не используются в новой модели. Старые накопления/долги превращаются в события с начальным прогрессом. Старые регулярные правила превращаются в события.

## 11. MVP этапы
A. Модель v3, миграция, pure calculator, тестируемые формулы.
B. Экран «Сейчас», настройки остатка/следующего дохода, статус и объяснение прогноза.
C. «Планы»: CRUD событий, регулярность, исполнение, цели и долги.
D. «Движение»: CRUD операций, категории, история, фильтры.
E. Ручная интеграция с задачами и экспорт JSON.
Автоматические списания, push-уведомления, банковские API, мультивалютность, синхронизация, импорт банковских выписок — вне MVP.

## 12. Приёмка
- Ручная сверка 100 000 ₽ на дату D плюс операции после D: auto остаток совпадает с базой + доходы − расходы.
- Переключение manual/auto не изменяет базовую сумму.
- Переводы и счета отсутствуют в UI и модели v3.
- Будущая аренда учитывается в прогнозе, но не становится фактическим расходом до исполнения.
- Ежемесячное событие 31-го числа корректно переносится на последний день короткого месяца.
- Два клика по исполнению одного наступления создают ровно одну операцию.
- Удаление/редактирование связанной операции корректно пересчитывает прогресс.
- Дни без операций участвуют в среднем как нули.
- При отсутствии ближайшего дохода статус gray.
- Старые данные мигрируют без повторного прибавления старых транзакций к текущему балансу.
